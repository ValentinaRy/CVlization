# Architecture

## Current scaffold

CVlization is a Manifest V3 extension built with TypeScript and Vite. It currently contains a toolbar popup and a dashboard that opens in a browser tab. It requests no permissions and has no network calls, background worker, website scripts, or persistence yet.

Vite compiles two HTML entry points into `dist/` and copies `public/manifest.json` unchanged. Type checking runs separately before production builds. Development uses a build watcher rather than a web server so the output can be loaded as an unpacked extension.

## Planned boundaries

- **Dashboard:** edit the profile, manage documents and templates, and review applications.
- **Content scripts:** inspect and fill supported forms, read an open vacancy or email on request. Site-specific adapters handle repeated experience groups and date controls.
- **Background worker:** coordinate browser events when features require it. Persistent state must not depend on worker memory.
- **Workspace storage:** read and write the user-selected directory through File System Access API.
- **Browser index:** cache summaries in IndexedDB for fast filtering. Rebuild from workspace records when needed; handle external edits with an explicit refresh.
- **Documents:** render a cover letter once, then use its text for form fields and generate a PDF locally for attachments.

Website scripts should receive only the data required for the selected operation, not access to the entire document archive.

## Planned workspace format

This folder is user data and must live outside the source repository.

```text
Job Search/
├── profile.json
├── documents/
│   ├── cv-en.pdf
│   ├── photo.jpg
│   └── diploma.pdf
├── templates/
│   └── cover-letters.json
└── applications/
    └── 2026-10-16_example-company_frontend_a1b2/
        ├── application.json
        ├── vacancy.txt
        ├── submitted-profile.json
        ├── resume.pdf
        ├── cover-letter.txt
        └── cover-letter.pdf
```

The profile will list document IDs, types, labels, languages, and workspace-relative paths, with defaults referring to IDs. Application records will have stable IDs, dates, statuses, and event history. Submission snapshots preserve the exact documents and text used, independently of later profile or template edits. Optional documents are created only when needed.

The workspace format will be versioned before real data is stored. File persistence is authoritative; the index is a derived cache. File access failures must be visible rather than reported as successful saves.

## Browser constraints

Brave may require `brave://flags/#file-system-access-api` to be enabled. Access and permission persistence must be tested in the actual browser. Moving or revoking access to a workspace should lead to a reconnect flow.

Standard file inputs can accept a file already read or generated by the extension. Custom uploaders need adapters and verification. Selecting a file may immediately upload it, so attachment actions must clearly identify the destination and document.

## Later integrations

Vacancy assessment starts with transparent keyword and requirement comparisons. External LLM processing is optional future work and must make outgoing data explicit. Missing information in a profile is not evidence that a person lacks a skill.

Email status suggestions use the currently open message and require confirmation. Matching must consider role and application identifiers, not just company name. There is no planned Gmail API connection.

LinkedIn support focuses on assessment of an open vacancy. Technical access does not imply platform permission; broader automation is exploratory and subject to platform rules.
